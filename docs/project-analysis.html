Source assessment · 28 Aug 2026 · v0.1.1 (code 2)

HyperLPA is a careful LPA trapped in files that are too large to change safely.

I read the app and JNI tree, not the vendored Miuix checkout. Backup crypto, reader affinity, privilege-split CI, and support-report redaction are better than most sideloaded eSIM tools. The thing that will hurt you next is not a missing TLS flag. It is OperationScreens.kt at 3,272 lines, LpaRepository.kt at 2,655, and a ViewModel with about 100 public methods.

Do this first

If this were my repo I would not start with Hilt, Argon2, or a settings rewrite. Five changes pay rent immediately.

  1. Finish the first-run reader gate. The compatibility wizard is already wired into NavDisplay, Routes.kt, and shouldOpenCompatibilityWizard(). It is still uncommitted on the working tree. Until it lands, discovery auto-connects the first available reader when lastReaderId is empty. Two cards on first launch can mean the wrong eUICC.
  2. Pin remote-reader TLS (TOFU). RemoCard already requires HTTPS and rejects userinfo, query, and fragment. Trust is still the platform CA store. APDU traffic is the crown jewels, and it is the one path that leaves the device on a URL the user typed.
  3. Slice the 3k-line Compose and repository files along seams you already have. downloadProfileBoundToReader and readerReconnectCandidateIds are the right cuts. Nobody can review a download path buried at line 745 of a 2,655-line file.
  4. Test the ViewModel’s download confirmation and navigation. Reconciliation helpers already have 539 lines of tests. The ViewModel has zero. The next regression will be “back stack and live download disagree after process death.”
  5. Run connected tests on API 28. CI uses API 35. The README promises 28+. Four existing instrumentation tests are enough to catch Compose/minSdk surprises.

Architecture

The package layout is honest: lpa for transports, data for stores, ui for Compose, provisioning for durable downloads. The problem is concentration. Six files over 1,000 lines hold more than 12,500 of the 26,964 production lines.

P1 One ViewModel owns the product

HyperLpaViewModel has about 100 public methods. Roughly 65 are one-line settings forwards from setThemeMode through setRemoteReaderToken. The rest mix navigation, reader connect, profile CRUD, batch download, backup, cloud icons, notification permission, and the wizard. MainActivity stuffs the whole application graph into its factory.

State is one HyperLpaUiState combined from 14 flows. That data class also sorts, filters, and applies optimistic profile-switch state. Search keystrokes therefore re-merge settings, metadata, and operator icon bytes. batchDownloadState already lives outside the blob, which is the team admitting the blob is awkward.

Keep a thin shell ViewModel for tab and snackbars. Split settings, provisioning, profiles, and backup. Move sort and filter out of the UI state class into a pure function. Generate the settings setters or pass AppSettingsStore into settings screens.

P1 The repository is the other god object

LpaRepository owns six reader backends, session lifecycle, notification delivery, SM-DS discovery, download confirmation, and activity logs. Inside it the design is careful: operationMutex, selectedReaderTargetId, reconnect candidates that refuse to fall through to a different card. That care is why the file is so hard to split, and why it must be split. The native lpac context is not thread-safe. The mutex belongs at a session layer, not in a 2,600-line kitchen.

Cut along ReaderDiscovery, EuiccSession, ProfileOperations, NotificationProcessor. Keep the mutex with the session.

P2 Manual DI is fine until the split

HyperLpaApplication is a 125-line graph. No Hilt, no Koin. At current size that is the right call. The moment you split the ViewModel you will copy constructor lists. Add Hilt then, not before.

P2 Navigation restore drops the high-stakes routes

Routes.kt is 52 lines and clean. Miuix NavDisplay is the right stack. Restoration is not. toPersistedRoute() maps CompatibilityWizard, ConfirmProfileDownload, ProfileDownloadResult, and history slots to null. Process death on a confirmation screen returns the user to the shell. The download job can survive in ProvisioningCoordinator. The UI does not reattach to it.

Persist the full back stack, or on restore, if a live or interrupted download exists, push the confirmation or batch route again.

P2 Business logic still lives in Compose

DownloadRequest.parse runs inside the download form around line 887 of OperationScreens.kt. Image QR scanning (field names carddata, activationCode) sits around 1090. Line 1976 hardcodes "GlobalPlatform" instead of a string resource. Split that file by screen. Put parse and scan in an ActivationCodeParser that unit tests already almost have.

Security

This area is stronger than the architecture. Android backup is off. Device-to-device extraction is excluded. Remote tokens sit in Keystore-backed AES-GCM with the endpoint URL as AAD. HyperLPA’s own backup strips those tokens. GSMA CI trust for ES9+ is the correct SGP.22 model, not a public-CA pin. The remaining holes are specific.

P1 Remote APDUs ride public CAs

RemoCardClient requires HttpsURLConnection, 15s/30s timeouts, 2 MiB caps, no redirects. There is no SPKI pin and no network_security_config. Payload “encryption” is AES-CBC with no MAC, documented as not a security boundary. The bearer token still goes on every request after handshake. Anyone who can MITM a user-chosen host with a valid cert sees APDUs.

Fix: TOFU pin when the user adds a host. Show the fingerprint. Store it. Replace CBC with TLS-only or an AEAD in a future RemoCard version. Stop sending the long-lived bearer after session establishment.

P2 Keystore tokens unlock in a pocket

RemoteCredentialCipher is the right shape: AES-256-GCM, 12-byte nonce, non-exportable key, setRandomizedEncryptionRequired(true). It does not set setUnlockedDeviceRequired(true). Tokens decrypt while the phone is locked. That is a product choice for headless readers. It is weaker than a screen-lock-bound key.

Fix: require an unlocked device at minimum. Biometric gating as an opt-in setting, default off.

P2 Backup KDF is 2023 OWASP

PBKDF2-HMAC-SHA256, 310,000 iterations, 16-byte salt, AES-256-GCM, 128-bit tag, AAD bound to format and version. Decrypt accepts 210k–1,000k iterations. Password floor is 10 characters. Ciphertext is zeroed. Fine for an offline file. Not what I would pick in 2026.

Fix: bump iterations on the next envelope version, or Argon2id via a small native helper. Keep the range check.

P2 JNI logs notification handles always

APDU logging in the app is gated on developerMode && apduLogging. USB verbose logs sizes, not hex. LocalProfileAssistantImpl still calls Log.d for notification handle and replay with no gate. Sequence numbers can land in logcat on user devices.

Fix: put those Log.d calls on the same verbose flow. Keep USB hex-free.

What I would leave alone

  • GSMA CI trust in HttpInterfaceImpl / RootCertificates.kt. Public-CA pinning would be wrong for ES9+.
  • HTTPS-only RSP URLs, no redirects, 32 MiB body cap, header injection checks. Test that a public-CA-only chain is rejected.
  • Privilege split. Ordinary APKs do not declare READ_PRIVILEGED_PHONE_STATE. CI greps both APKs. Hidden API exemptions are flavor-gated.
  • nineesim-keystore.properties is gitignored. The community-key passwords in the release workflow are public by design.
  • Manifest usesCleartextTraffic="false". No debug network-security override in app resources.

Reliability

Three process-death stories, only one of them complete.

LayerWhat survivesGap
Backup restore journal HyperLpaApplication.onCreate runBlocking recovers a two-DataStore restore before UI starts. Orphaned icon cleanup waits until the journal is clear. This is the most careful startup code in the app. Leave the structure.
Provisioning queue Keystore AES-GCM in noBackupFilesDir. FGS is START_NOT_STICKY so Android will not replay an activation code. Recovered batches need explicit Resume. Affinity checks block the wrong card. After death, the UI does not reopen Batch / Confirm. The user has to find the interrupted job.
Navigation Selected tab and a subset of settings routes in onSaveInstanceState. Confirmation, result, wizard, search query, and activation draft do not survive process death.

P2 USB runBlocking { verboseLoggingFlow.first() } on a hot path can stall if the flow never emits. Snapshot verbose logging into a volatile Boolean updated from settings, the way LpaRepository.verboseLoggingEnabled already does.

P2 Auto-connect after first selection is locked to that reader. Initial selection is not. If lastReaderId is unset, readerReconnectCandidateIds falls through discovery order across six providers. That is the wizard’s job. Finish it, and refuse auto-connect when more than one reader is available.

Tests

The ratio is about 9 production lines per unit-test line. That would be acceptable if the 9 were UI and the 1 were domain. It is the opposite. Helpers are well tested. The cores are not.

Covered

Backup codec, settings validation, provisioning models, metadata store, notification history sanitization, support-report redaction, repository reconciliation (539 lines), download-request parsing, Nekoko helpers, USB parsing, NBridge trust, remote-reader crypto helpers, reminder isolation, RSP URL validator, SM-DP+ cert verifier, ASAN/UBSAN host tests for derutil and the profile parser. Those native tests are hooked to testDebugUnitTest, so CI actually runs them.

The hole

Zero tests for HyperLpaViewModel. No tests for LpaRepository.connect, downloadProfile, or notification send. No tests for OMAPI, telephony, or the BLE provider beyond policy snippets. LpaEngineTest is 29 lines of AID hex decode. Four instrumentation tests, 179 lines, API 35 only. Wizard instrumentation is uncommitted.

Highest-value next test: a fake ApduInterface plus HttpInterface around LocalProfileAssistantImpl. Then a ViewModel test with a fake coordinator for navigation and download confirmation. Then an API 28 emulator job, even if it only runs the four existing tests.

UI and product chrome

Miuix is not a skin here. Theme, blur, NavDisplay, predictive back, snackbars, and preference cards are the real stack. The screens are too big for the quality of the toolkit.

  • P1 OperationScreens.kt is 42 functions in one file. Split download, details, eUICC, and QR. The wizard is 240 lines, already reachable from Tools, with swipe-dismiss disabled. Land it as a first-run gate or take the route out until it is done.
  • P2 Only values/strings.xml. RTL is declared. A HyperOS-styled LPA with no Chinese strings is a product mismatch. Extract is done. Add values-zh-rCN before adding more English literals.
  • P2 Profile cards and hidden-label nav items have contentDescription. Many icons still pass null. Download confirmation is a high-stakes screen and should be read as operator, redacted ICCID, confirm, cancel.
  • P3 CenteredBox takes maxWidth and ignores it. The modifier chain is .then(Modifier), a no-op. Tablets get a centered phone layout. There is no list-detail two-pane at 1200.dp even though WindowMode.EXPANDED exists.
  • P3 Remaining literal: "GlobalPlatform" in eUICC details. QR JSON keys are protocol, not UI copy.

Build and CI

Release packaging is unusually serious for a 0.1 app: ABI splits, community vs private signing, certificate pinning in Gradle, permission greps, apksigner v3 checks, SHA256SUMS on GitHub Releases. The gaps are about what CI does not run, not what it signs.

  • P1 Connected tests only on API 35. Release workflow runs no connected tests. No screenshot tests (Paparazzi / Roborazzi).
  • P3 lpac-jni hardcodes core-ktx:1.19.0 and coroutines instead of the version catalog. App is Java 21. JNI module is Java 17. Document that or align them.
  • P3 App ProGuard only keeps source/line attributes. JNI consumer keeps look complete. A smoke test that a minified APK can still System.loadLibrary and construct LocalProfileAssistantImpl would catch a keep-rule miss before a tag.
  • P3 Spotless lives under third_party/miuix only. Do not add detekt until the 3k-line files are split. It will only generate noise.
  • httpProxyFlow is passed as flowOf("") from LpaSessionFactory. Proxy support is dead. Wire it or delete it.

Product

HyperLPA already covers the EasyEUICC-class core: list, enable, disable, delete, rename, activation codes, QR, lpa: links, notifications, SM-DS, default SM-DP+, memory reset, confirmation codes, IMEI in download, batch queue, tags, reminders, redaction, encrypted backup. That is a lot for version 0.1.1.

What is still missing, relative to a “full” LPA:

  • P2 First-run multi-reader choice. Always show the connected EID in the top bar. Disable auto-connect when readers.size > 1.
  • P2 MEP as a first-class UI. Telephony ports are listed. There is no “enable this profile on port 2” model.
  • P2 App lock before showing ICCID and EID, even with redaction settings. People will screenshot the details page.
  • P2 No Android EuiccManager / downloadable-LPA path. Fine if that is a deliberate non-goal. Say so in the README so carrier-download expectations die early.
  • P3 Offline: local list and metadata work. Auto notification send already checks NET_CAPABILITY_VALIDATED. The download screen still lets the user type a confirmation code before failing. Disable Download and Process notifications when unvalidated, with a reason.
  • P3 README is unusually good. Gaps: RemoCard server setup, how to install the privileged APK on a system image, activation-code anatomy (LPA:1$…), and what the wizard will do.

Order of work

Leave PBKDF2, manual DI, and GSMA-CI TLS alone until the list below is done. They are not why a change in this codebase is scary. The 3,272-line Compose file is.

  1. Land the wizard, or hide the route. No auto-connect when multiple readers exist.
  2. TOFU pin for remote readers.
  3. Split OperationScreens.kt and LpaRepository.kt along existing types.
  4. ViewModel tests for navigation plus download confirmation, with a fake coordinator.
  5. API 28 connected job.
  6. Chinese strings. The toolkit is Miuix. The only locale is US English.
  7. Then, if you still want it: Hilt with the ViewModel split, iteration bump on backups, tablet two-pane, dead CenteredBox / proxy flow cleanup.

This is a 0.1.1 that already behaves like a 1.0 on security hygiene and release engineering. Treat the god files as the actual 0.2 milestone. Everything else is polish on a product people can already trust with a card, as long as they only plug in one.
